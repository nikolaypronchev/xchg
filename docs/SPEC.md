# ТЗ: xchg v2 — «несколько хабов, один клиент»

## 1. Зачем

Сегодня есть один обменник `agents-exchange` (git-репо на dev, группа tr-devs): люди и их агенты
Claude Code обмениваются сообщениями через файлы, знание проектов лежит в `projects/<p>/`.
Клиент `bin/xchg` живёт внутри того же репо.

Нужно то же самое, но для нескольких независимых кругов общения одновременно:

| круг | кто | где живёт |
|---|---|---|
| личный | мои агенты на моих машинах | свой сервер (senko/mc) или любой git-хостинг |
| работа | коллеги по tr-devs | dev:/opt/trends/agents-exchange (уже есть) |
| хобби / пет-проекты | внешние люди без доступа на dev | приватный репо на GitHub/Gitea/… |

Требования пользователя: единая сеть, из одного места отправлять письма агентам и людям
в любом круге, видеть, чем заняты мои агенты, делиться знанием. При этом круги не должны
протекать друг в друга.

## 2. Термины

- **Хаб** — один git-репозиторий с контрактом agents-exchange. Хаб = круг доверия = список тех,
  у кого есть push. Хабы независимы, между ними нет автоматического обмена.
- **Клиент** — `xchg`: CLI + скилл Claude Code + хуки. Один на машину, знает все хабы пользователя.
- **Человек** — `people/<login>/` в хабе. Логин локален для хаба (на работе `pronchev`, в хобби может
  быть `kolya`).
- **Агент** — репозиторий, над которым работает Claude Code, а не сессия. Все сессии, клоны,
  worktree и машины на одном репо — один агент с общей рабочей памятью (L2). Идентичность =
  `<человек>/<basename репо>` (`pronchev/trends`).
- **Адрес** — `[хаб:]получатель`, получатель ∈ { `login` | имя/алиас из contacts | `all` | `@project`
  | `login/agent` (только в хабах, где включены агентские ящики) }.

## 3. Не делаем (сознательно)

- **Реле между хабами.** Никаких серверов-посредников, cross-hub identity, «настоящей» федерации.
  Мост между кругами — человек, состоящий в обоих; перенос делается явно (`xchg forward`).
- Веб-интерфейс, БД, HTTP API, MCP-сервер. Git — единственный транспорт. (MCP-обёртку можно
  добавить позже поверх того же CLI.)
- Опрос ящика по таймеру из модели (`/loop`, cron-агенты): каждый тик — ход модели, токены уходят
  и на пустом ящике. Уведомления только через хуки с пустым выводом при пустом ящике.
- Автопубликация статуса агентов в общие (не личные) хабы.
- Шифрование содержимого. Приватность обеспечивается членством в хабе.

## 4. Архитектура

```
~/.config/xchg/xchg.conf         реестр хабов (у пользователя, не в git)
~/.local/bin/xchg                клиент (симлинк или копия из репо xchg)
~/.claude/skills/exchange/       скилл (симлинк из репо xchg)
~/exchange/<hub>/                клон каждого хаба (путь настраиваемый)
```

Клиент и скилл выносятся из хаба `agents-exchange` в **отдельный репо `xchg`** (этот проект).
Хаб хранит только данные и контракт. Обновление клиента — `git pull` в репо xchg
(автоматически при `xchg inbox`, как сейчас, но по своему репо).

### 4.1 Реестр хабов и зависимости

Клиент — один bash-скрипт. Зависимости: `bash ≥ 4`, `git`, `awk`, `sed`, `coreutils`. Это есть
везде, где есть Claude Code (Linux, macOS, WSL, Git Bash на Windows). Необязательные:
`python3` — только для регистронезависимого поиска кириллицы в contacts (без него — точное
совпадение или латиница), `jq` — только для правки `settings.json` в `install` (без него печатается,
что вписать руками). Никаких TOML/YAML-парсеров: конфиг — INI-подобный, читается awk.

```ini
# ~/.config/xchg/xchg.conf   (на Windows/Git Bash тот же путь под $HOME)
host    = nb-wsl          # идентификатор этой установки, §4.9
default = work            # хаб для адресов без префикса, если по contacts не однозначно

[hub me]                  # личный хаб; создаётся install'ом ЛОКАЛЬНО, без remote
path    = ~/exchange/me
login   = pronchev
agents  = true

[hub work]
remote  = dev:/opt/trends/agents-exchange
path    = ~/exchange/work
login   = pronchev

[hub hobby]
remote  = git@github.com:someone/exchange-hobby.git
path    = ~/exchange/hobby
login   = kolya
```

Грамматика: `key = value`, секции `[hub <name>]`, комментарии `#`, пробелы вокруг `=` не значимы,
`~` в путях раскрывается. Всё остальное — ошибка с номером строки.

**Личный хаб по умолчанию локальный:** обычный git-репо без remote в `~/exchange/me`. `store push`
коммитит локально. Когда нужно делить между машинами — `xchg hub remote me <url>` добавляет
origin и пушит; с этого момента `sync` ходит на сервер. Хаб без remote в `sync` пропускается молча.

Обратная совместимость: если `xchg.conf` нет, но есть `~/exchange/.git` — считать его единственным
хабом `work` с `login = git config xchg.me || $USER`. Коллеги с текущей установкой ничего не делают;
`install` создаёт `xchg.conf` из этого состояния.

### 4.2 Раскладка хаба (контракт v2 = v1 + агенты)

```
README.md                    контракт хаба (копия эталона из репо xchg, версия в шапке)
contacts.md                  login ↔ имя ↔ алиасы ↔ проекты ↔ контакт
people/<login>/inbox/        письма человеку (любой его агент забирает)
people/<login>/README.md     (опц.) о человеке
people/all/inbox/            broadcast
projects/<p>/inbox/          очередь «кому-нибудь на проекте»
projects/<p>/*.md            общее знание: status.md, decisions.md, handoff_*.md, …
agents/<login>/<agent>/inbox/       письма конкретному агенту              (только agents = true)
agents/<login>/<agent>/<store>/     приватные хранилища агента, см. §4.8    (только agents = true)
  memory/SESSION.<host>.md            пример: L2 памяти, файл на хост (пишет пакет памяти, не xchg)
```

Формат сообщения — без изменений (frontmatter `from/to/project/date/re`), плюс:
- `from` может быть `login/agent`;
- `hub:` не пишется в файл — письмо принадлежит хабу, в котором лежит;
- `forwarded_from: <hub>/<original path>` при `xchg forward`.

Семантика `done` — как в v1: файл общий, `done` закрывает для всех.

### 4.3 Адресация и резолв

1. Разобрать `[hub:]rcpt`. Если хаб указан — искать только в нём.
2. Без хаба: `rcpt` = `all`/`@p` → хаб `default`. Иначе искать `rcpt` по `people/` и `contacts.md`
   всех хабов (casefold, кириллица). Ровно одно совпадение → ок. Несколько → ошибка с перечнем
   («оля есть в work и hobby, уточни `work:оля`»). Ноль → ошибка «xchg who».
3. `login/agent` допустим только в хабах с `agents = true`; иначе ошибка.

### 4.4 Идентичность агента

- `XCHG_AGENT` в окружении → используется как есть.
- Иначе: basename основного репозитория от cwd — `basename $(dirname $(git rev-parse --git-common-dir))`
  (для worktree это даёт имя главного репо, а не worktree); вне git — `shell`.
- Никаких суффиксов по worktree/ветке/PID: параллельные сессии — один агент. Их согласование —
  через общий SESSION.md (блок NOTE), как в протоколе памяти.
- **Коллизия имён — явная ошибка.** `~/.config/xchg/agents.conf` — реестр `имя = origin URL`
  (нормализованный: без `.git`, схемы и учётки). Первый вызов `xchg agent` из репо регистрирует пару.
  Если имя занято репо с другим origin — код возврата 3 и сообщение:
  «агент `api` уже привязан к `dev:/opt/trends/api`; для этого репо задай алиас:
  `xchg agent set <имя>`». Алиас хранится в самом клоне (`git config xchg.agent`), не коммитится;
  на другой машине его нужно задать так же (иначе там будет та же ошибка — это намеренно).
  Репо без origin регистрируется по абсолютному пути.
- `from` в общих хабах — только `login` (агент не раскрывается); в хабах с `agents = true` —
  `login/agent`.

### 4.5 Доска статусов (личный хаб)

Отдельного файла статуса нет: доска выводится из `agents/<login>/<agent>/memory/SESSION.*.md`
(§4.8) — по одному, самому свежему файлу на агента, с указанием host. Это **конвенция формата**,
а не зависимость от пакета памяти: board показывает frontmatter `last_updated`, заголовок `# Goal`
и строку `last action` из `# State`, если они есть; иначе — только имя файла и дату.
`xchg board [hub]` — таблица: agent, host, `updated` (относительное), Goal, last action.
Устаревшие (> 24 ч) помечаются; агент, активный на другом host < 30 мин назад, помечается «активен». `xchg inbox --brief` при старте сессии
печатает доску одной строкой на агента, если она изменилась с прошлого показа, иначе молчит.

### 4.6 Уведомления (без токенов)

Как в v1, но по всем хабам: `SessionStart` без дебаунса, `UserPromptSubmit` с `--max-age 300`.
Пустой результат по всем хабам → пустой вывод. Синхронизация хабов параллельная (fetch всех
сразу), общий таймаут 20 с; недоступный хаб не валит остальные, печатается одна строка
«hub X недоступен» не чаще раза в час.

### 4.7 Перенос между хабами

`xchg forward <file> <hub:rcpt> [--note "…"]` — копирует письмо как новое от текущего пользователя
в другой хаб с `forwarded_from`, оригинал не трогает. Знание переносится копированием файлов
руками/агентом; клиент этому не помогает намеренно (см. §3).

### 4.8 Личный хаб как приватное хранилище агента (`store`)

xchg **не знает** о системе памяти. Он даёт два примитива, которыми память (или любой другой
инструмент) пользуется:

- `xchg agent` — печатает идентичность `login/agent` (§4.4).
- `xchg store pull|push <dir> --as <name>` — синхронизирует локальный каталог с
  `agents/<login>/<agent>/<name>/` личного хаба. Каталог переносится как есть (`rsync`-подобно,
  удаления учитываются). `push` = pull --rebase + commit `[store] agent/name@host` + push.
  Дебаунс не применяется: вызовов мало, данные важные.

**Правило отсутствия конфликтов — файл на хост.** Клиент не мёржит содержимое. Инструмент,
который кладёт данные в store, обязан писать в файлы, имя которых включает `host` (§4.9):
`SESSION.<host>.md`, `notes.<host>.md`. Тогда две машины никогда не правят один файл, и
`pull --rebase` проходит всегда. Слияние смысла (какое состояние актуально) делает читатель:
самый свежий по `last_updated`/mtime — актуальный, остальные — контекст. `xchg store push`
отказывается пушить файл без `.<host>.` в имени, если в каталоге есть одноимённый файл другого
хоста (защита от случайного общего файла); `--force-shared` снимает проверку.

Если конфликт всё же возник (общий файл, нарушение правила) — хук не оставляет маркеры в файлах:
локальная версия сохраняется как `<file>.conflict.<host>`, чужая принимается, печатается
предупреждение.

**В хаб НЕ попадают:** L0 (`IDENTITY.md`), L1 в репо (`CLAUDE.md`, `.claude-docs/` — едут с кодом),
L1-fallback (`project.md`). В общих хабах (`agents = false`) `store` недоступен.

Граница между L1 и `projects/<p>/` хаба: знание об одном репо живёт в этом репо; знание,
связывающее несколько репо или людей (контракты API, кто что делает), живёт в хабе.

### 4.9 Идентификатор хоста

`host` — короткое имя **установки клиента**, не машины: `[a-z0-9-]{2,24}`, lowercase.
Задаётся один раз в `xchg.conf` командой `xchg install` (или `xchg host set <name>`) и **никогда
не вычисляется заново**. Причины не полагаться на `hostname`:
- под WSL `hostname` = имя Windows-машины → WSL и нативный Windows на одном ПК неразличимы;
- `DESKTOP-K3J2X1` и подобные — нечитаемы и могут меняться;
- один ПК с двумя ОС/двумя пользователями — это разные установки.

`install` предлагает значение по умолчанию `<hostname lowercase>-<os>`, где os ∈ `wsl`
(`/proc/version` содержит `microsoft`), `linux`, `mac` (`darwin`), `win` (`$OSTYPE` msys/cygwin),
и просит подтвердить или ввести своё (`nb-wsl`, `desk-win`, `mac`). Перед сохранением проверяет
по личному хабу, что такого host ещё нет среди `agents/<login>/*/*/*.<host>.*` — иначе ошибка.
`xchg host` печатает текущий; `xchg hosts` — все host, встречающиеся в личном хабе, с датой последней
активности. Переименование — `xchg host rename <old> <new>` (переписывает имена файлов в хабе).

## 5. CLI

```
xchg inbox [--brief] [--max-age N] [--hub H]      сводка по всем хабам / одному
xchg read <hub:file | file>                      файл однозначен по префиксу пути хаба
xchg send <[hub:]rcpt> <slug> [--project p] [--re file] < body
xchg done <hub:file | file>
xchg forward <file> <hub:rcpt> [--note …]
xchg who [query] [--hub H]                       contacts всех хабов, с колонкой hub
xchg board [hub]                                 доска агентов (из memory/SESSION.<host>.md, конвенция)
xchg agent                                       идентичность login/agent для текущего cwd
xchg store pull|push <dir> --as <name> [--force-shared]   приватное хранилище агента в личном хабе
xchg host | host set <name> | host rename <old> <new> | hosts
xchg hubs | xchg hub add <name> <remote> [--login L] [--agents] | xchg hub rm <name>
xchg projects [--hub H]
xchg log [n] [--hub H]
xchg sync [--hub H]
xchg status                                      сам клиент: версия, хабы, свежесть, хуки
xchg install                                     симлинки + хуки, идемпотентно
xchg version
```

Вывод `inbox`: колонки `hub  scope  file  from  title`; `scope` ∈ me/agent/all/@project.

Ошибки — на stderr, код ≠ 0; сообщения на русском, с подсказкой следующей команды.

## 6. Скилл `exchange`

Один скилл на все хабы. Должен объяснять агенту: адресацию с префиксом хаба, что `from`
в общих хабах — человек, правило «неоднозначный адресат → спросить пользователя», доску, и что
опрашивать ящик по таймеру нельзя. Обновляется вместе с клиентом.

## 7. Установка и обновление

- `git clone <repo xchg> ~/.xchg && ~/.xchg/bin/xchg install` → симлинки, хуки, создание
  `xchg.conf` из существующего `~/exchange` (миграция v1) либо пустого шаблона.
- `xchg hub add work dev:/opt/trends/agents-exchange` клонирует и регистрирует.
- Клиент обновляет сам себя: `sync` делает `git pull` и в репо xchg (дебаунс тот же), при
  изменениях печатает «клиент обновлён» + коммиты. Хаб больше не содержит `bin/`.
- Версия контракта — в шапке `README.md` хаба (`contract: 2`). Клиент отказывается писать в хаб
  с более новым контрактом, чем знает.

## 8. Безопасность и приватность

- Хаб = круг доверия; никакого содержимого одного хаба не попадает в другой без явного `forward`.
- `from` в общих хабах не раскрывает имя агента/репозитория/ветки.
- Автостатус только при `agents = true`; в личном хабе по умолчанию, в остальных — нет.
- Секреты в письма не кладём (правило контракта), клиент дополнительно предупреждает, если тело
  похоже на токен (`AKIA…`, `ghp_…`, `-----BEGIN`), но не блокирует.
- `xchg.conf` вне git; ключи — обычные ssh-ключи пользователя.

## 9. Миграция с v1

1. Репо `agents-exchange` на dev: `bin/` и `.claude/` удаляются, README получает `contract: 2`,
   раскладка `people/projects` не меняется. Коллегам: один раз `git clone xchg && xchg install`
   (миграция `~/exchange` → хаб `work` автоматическая).
2. Переходный период: старый `bin/xchg` в хабе оставить на 2 недели с сообщением «клиент переехал,
   выполни …» при каждом запуске.

## 10. Этапы

| # | что | критерий готовности |
|---|---|---|
| 1 | Репо `xchg`: клиент вынесен, `xchg.conf`, префиксы, сводный inbox, `hub add/rm`, миграция v1 | С двумя хабами (dev + локальный bare) send/inbox/done/who работают, без реестра ведёт себя как v1 |
| 2 | Скилл v2, `install` с двумя хуками, самообновление клиента | Коллега ставит по инструкции из README за 2 команды, обновления видит без действий |
| 3 | Личный хаб: `agents = true`, агентские ящики, `agent`, `host`, `store pull/push`, `xchg board` | Два host пушат в один store параллельно без конфликтов; доска показывает свежайший файл на агента с host |
| 3b | (пакет памяти) slug по агенту, `SESSION.<host>.md`, pull/push в хуках, миграция | Один агент с двух ПК: сессия на втором видит состояние первого как NOTE и предупреждение «активен» |
| 4 | `forward`, предупреждение о секретах, `xchg status` | e2e: письмо из work переслано в hobby с `forwarded_from` |
| 5 | Миграция хаба на dev, уведомление коллег | Старый `bin/xchg` печатает подсказку, новый клиент у всех |

## 11. Приёмочные сценарии

1. «Отправь Оле, что контракт готов» — агент резолвит `оля` → `work:atanova`, если `оля` есть только
   в work; при наличии в двух хабах — спрашивает.
2. Старт сессии в репо `trends`: агент видит письма из всех хабов и доску личных агентов;
   при пустых ящиках вывод хуков пустой (проверить: 0 байт).
3. Агент `pronchev/matcher-mvp` закончил ход на `nb-wsl` → на `desk-win` сессия в том же репо стартует,
   читает `SESSION.nb-wsl.md` как актуальное состояние, пишет своё в `SESSION.desk-win.md`; оба host
   пушат по очереди и одновременно — ни одного конфликта; `xchg board me` показывает nb-wsl как свежайший.
6. WSL и нативный Windows на одном ПК установлены оба → у них разные `host`, `install` второго не даёт
   выбрать занятое имя.
4. Хаб `hobby` недоступен (нет сети) — `inbox` показывает остальные хабы, одна строка про
   недоступность, код возврата 0.
5. Клиент v2 против хаба v1 (без `contract:` в README) — работает в режиме совместимости.

## 12. Интеграция с claude-memory-3layer (потребитель, отдельная задача)

Зависимость односторонняя: память → xchg, необязательная. Без xchg память работает как сейчас.
Правки в пакете памяти:

1. `session-start.sh`: slug = `agent--<login>--<agent>` из `xchg agent`, если xchg есть и есть личный
   хаб; иначе — из пути, как сейчас. Перед чтением — `xchg store pull ~/.claude/projects/<slug>/memory --as memory`.
2. L2 пишется в `SESSION.<host>.md` (`host` из `xchg host`). При старте читаются все `SESSION.*.md`:
   самый свежий по `last_updated` — рабочее состояние, остальные — блок NOTE «на <host> было: Goal…».
   Если чужой `last_updated` моложе 30 мин — явное предупреждение «агент активен на <host>».
3. `Stop` и `PreCompact`: после записи — `xchg store push … --as memory`.
4. Ротация/архив — по-хостово: `SESSION.<host>.archive*.md`.
5. Миграция существующих `~/.claude/projects/<slug>/memory/` → новые slug: скрипт по таблице
   «путь → репо», старые каталоги остаются read-only на месяц.

## 13. Решённые вопросы (для истории)

- Парсер конфига: свой INI на awk, без TOML. Клиент — чистый bash, python3/jq необязательны.
- Коллизия одноимённых репо: явная ошибка, разрешается алиасом `xchg agent set` в клоне.
- `*:all` (broadcast во все хабы разом): не делаем — круги независимы, рассылка в каждый явная.
- Личный хаб: по умолчанию локальный репо без remote, вынос на сервер — `xchg hub remote me <url>`.
- Remote самого проекта `xchg`: Николай скажет по готовности.
